# База даних Shopik

## Заплановано: авторські права та незалежна історія витрат (011)

Цей розділ задає нові вимоги; міграції для них ще немає. Нижче описано фактично реалізовані етапи 001–007, чиї загальні дозволи учасникам і каскади не забезпечують нові правила.

- Для звичайного UPDATE/DELETE продукту потрібні чинне членство та `created_by = auth.uid()`. Такі ж авторські обмеження мають поширюватися на RPC і зміни `product_tags`. Власник не може обходити їх звичайним запитом. Право завершення потребує уточнення в задачі 011.
- Окрема операція виключення доступна лише власнику, атомарно видаляє членство, продукти й категорії цільового учасника лише в заданому Workspace. Потрібні захист від конкурентних мутацій і повторного виконання та безпечне вирішення чужих продуктів у видалених категоріях.
- Витрати завершених продуктів виключеного учасника зберігаються. Звичайне видалення продукту продовжує видаляти його витрату. Розрізнення цих операцій не повинно керуватися довільним клієнтським прапорцем.
- Чинні `expenses.product_id` із `ON DELETE CASCADE`, зв'язок продукту з обов'язковою категорією та фільтри через `product_tags` потрібно переглянути. Цільова історія не залежить від існування вихідного продукту/категорії/членства; зберігає знімки назви, автора, суми, валюти, дати, ідентичності й назви категорії та тегів для AND-фільтрації. Конкретні таблиці й FK визначаються в задачі 011.
- Міграція зберігає наявні записи, дати й суми. Після виключення загальні та фільтровані місячні підсумки в `Europe/Kyiv` не змінюються; доступ має лише поточне членство. Відкликання членства блокує також відкладені операції офлайн-черги.

Перед реалізацією погодити перенесення чужих продуктів із категорій виключеного учасника та права на видалення збережених архівних витрат. Детальні критерії й відкриті питання — `docs/tasks/011-shared-workspace-permissions.md`.

## Етап 007: особиста тема

Міграція `202610290007_account_settings.sql` додає `profiles.theme text NOT NULL DEFAULT 'light'` з CHECK тільки `light`/`dark`. Grant UPDATE розширюється лише на цю колонку; RLS профілю залишається self-only, без змін доступу до ролей, авторів, тегів чи категорій. Server Action перевіряє claims і сам визначає user ID, не приймаючи його від клієнта.

Тема не належить Workspace. Cookie `shopik-theme` (HttpOnly, SameSite=Lax, Secure у production, строк 1 рік) зберігає локальне оформлення; після входу профіль має пріоритет. Root layout читає тему на сервері й віддає `data-theme` та color-scheme в початковому HTML. Зміна cookie виконується тільки після успішного збереження профілю. Дані тегів/категорій при перенесенні інтерфейсу в налаштування не мігруються та не дублюються.

SQL-тест `supabase/tests/account_settings.sql` перевіряє особисте оновлення, ізоляцію двох акаунтів, валідацію, анонімний доступ та незмінність теми при синхронізації Google metadata.

## Уточнення етапу 006

Міграція `202610290006_logic_ui.sql` забороняє зміни завершених продуктів та їхніх тегів тригерами й RPC. Повторний запит завершення залишається ідемпотентним; видалення дозволено й каскадно прибирає витрату та зв'язки тегів. `filtered_products` повертає тільки active. Зв'язок завершеної покупки з категорією збережений, тому така категорія не вважається порожньою для видалення.

`profiles.avatar_url` заповнюється з публічних Google metadata під час міграції та синхронізується тригером auth.users. Наявні display_name не перезаписуються, якщо вони непорожні. Політика прямого читання профілів лишається self-only. RPC `workspace_product_authors(workspace_id)` повертає тільки product_id, ім'я, аватар і початковий created_at авторів продуктів дозволеного Workspace; перевіряє членство й не відкриває auth.users, email чи всі профілі.

Нижче збережено опис попередніх етапів; правила повернення в active з етапу 004 замінено цим уточненням. SQL-тести актуалізовані, новий тест — `supabase/tests/logic_ui.sql`.

Вимоги в документації є джерелом правди; початкові локальні тестові записи не визначають схему бази. Нижче окремо описані реалізовані та заплановані сутності.

## Етап 1: авторизація та особистий Workspace

Джерело схеми: `supabase/migrations/202610290001_auth_workspaces.sql`.

| Таблиця | Поля та зв'язки |
| --- | --- |
| `auth.users` | Користувач Supabase Auth; вхід тільки через Google |
| `profiles` | `id` → `auth.users.id`, `display_name`, `created_at` |
| `workspaces` | `id`, `name`, `owner_id` → `auth.users.id`, `is_personal`, `created_at` |
| `workspace_members` | `workspace_id`, `user_id`, `role` (`owner` / `member`), `created_at`; складений первинний ключ |

ID цих сутностей — UUID. Вимога SHA256 для ID продуктів застосовуватиметься до таблиці продуктів наступного етапу.

Частковий унікальний індекс дозволяє рівно один особистий Workspace на власника, залишаючи можливість кількох спільних просторів у майбутньому.
RPC `ensure_personal_workspace()` створює профіль, особистий Workspace і членство `owner` в одній транзакції. Повторні виклики не створюють дублікати. User ID береться виключно з `auth.uid()`.

RLS:
- анонімні користувачі не мають доступу до таблиць і RPC;
- профіль читає й змінює лише його власник; змінювати дозволено тільки `display_name`;
- Workspace та його учасників читають лише члени цього Workspace;
- пряме створення та редагування Workspace/членства через Data API заборонено;
- функції `security definer` мають порожній `search_path` і явні дозволи виконання;
- ролі не визначаються через редаговані користувачем OAuth metadata.

Паролі Shopik не отримує й не зберігає. Авторизацією та сесіями керує Supabase Auth.

## Етап 2: продукти

Міграція: `supabase/migrations/202610290002_products.sql`. Вона створює порожню таблицю без демонстраційних даних. Старий `shopik-app/data/product.json` видалений; його записи не імпортуються.

`products`:
- `id`: 64 hex-символи SHA256, база генерує з двох випадкових UUID;
- `workspace_id`: UUID простору;
- `created_by`: UUID автора, база бере з `auth.uid()`;
- `name`: обрізана по краях назва, 1–120 символів;
- `description`: необов'язковий опис до 2000 символів, порожній рядок за замовчуванням;
- `price`: PostgreSQL numeric від 0 до 99 999 999,99, максимум два десяткові знаки; зайві знаки відхиляються без округлення;
- `currency`: тільки `UAH`;
- `status`: `active` / `completed`, початково `active`;
- `created_at`, `updated_at`: часові позначки бази, тригер оновлює `updated_at`.

Учасники Workspace можуть читати, створювати, редагувати, завершувати та видаляти його продукти. RLS перевіряє членство для кожної операції. Column grants забороняють клієнту підмінити ID, автора, Workspace, валюту й часові позначки. Server Actions додатково перевіряють сесію та членство.

## Етап 004: категорії та витрати

Міграції `202610290003_categories.sql` і `202610290004_expenses.sql` застосовуються по черзі після попередніх. Код готовий; застосування та перевірки фіксуються в `docs/tasks/004-categories.md`.

`categories`: UUID `id`, `workspace_id`, назва 1–120 символів, `created_by`, `created_at`, `updated_at`. Назва унікальна без урахування регістру в межах Workspace. Тригер створення Workspace атомарно додає «Обов'язкові покупки»; повторний вхід не відновлює видалені категорії. Одноразова міграція створює категорії для існуючих просторів і прив'язує наявні продукти без видалення даних.

`products.category_id` обов'язковий. Складений зовнішній ключ `(workspace_id, category_id)` забороняє чужу категорію; `ON DELETE RESTRICT` захищає непорожню категорію навіть при конкурентних запитах. RLS дозволяє CRUD категорій лише учасникам Workspace; column grants не дозволяють підмінити власника чи простір.

`expenses`: UUID `id`, `workspace_id`, унікальний `product_id`, знімки `name`, `category_id`, `category_name`, `amount`, `currency`, `occurred_at`. Історична назва категорії не залежить від її поточного перейменування. Складений FK на продукт із `ON DELETE CASCADE` прибирає витрату при видаленні продукту. Повернення продукту в активні теж прибирає витрату. Нове завершення створює новий знімок; повторний запит completed не дублює запис.

Тригер бази синхронізує статус і витрату в одній транзакції. Прямий запис expenses для authenticated заборонений; читання захищене RLS. RPC `expense_month(workspace_id, month)` працює як security invoker, перевіряє членство та підсумовує PostgreSQL numeric за напіввідкритим інтервалом місяця в `Europe/Kyiv`. Повертає загальну суму, суми за історичними категоріями й покупки. Порожній місяць дає нуль і порожні списки.

Для наявних completed-продуктів міграція використовує `updated_at` як останню відому дату завершення; точніші історичні дати раніше не зберігались.

## Наступні етапи

Запрошення, теми, вага, колір та іконки продуктів — окремі задачі. Зв'язки мають залишатися в межах одного Workspace.

## Етап 005: теги

Міграція `202610290005_tags.sql` додає `tags` (UUID ID, Workspace, назва 1–120 символів, колір `#RRGGBB` у верхньому регістрі, автор і часові позначки) та `product_tags` (Workspace, продукт, тег). Назви унікальні без урахування регістру в межах Workspace. Складені зовнішні ключі забороняють зв'язки між різними Workspace; первинний ключ забороняє повтор тегу в одному продукті. Видалення продукту видаляє зв'язки, але не теги.

RPC `save_product_tags` атомарно зберігає поля продукту й повний набір тегів, блокуючи рядок при редагуванні. `filtered_products` застосовує категорію та всі вибрані теги (AND) на сервері й повертає продукти з кольоровими тегами. Невідомі або чужі теги відхиляються, а не вилучаються з фільтра.

`expense_month_tags` використовує поточні зв'язки тегів продукту та історичні суми витрат. Відбір відбувається до агрегації; кожна витрата рахується один раз незалежно від кількості тегів. Старий `expense_month` збережений як виклик без тегового фільтра. Усі функції — security invoker з перевіркою членства та RLS; search_path порожній.

Наявні продукти початково не мають тегів; дані не видаляються. SQL-тест `supabase/tests/tags.sql` перевіряє ізоляцію двох користувачів, складені FK, атомарний відкат при помилці зв'язків, AND-фільтри, суми без дублів і збереження тегів після видалення продукту.

## Етапи 008–009: ідемпотентні операції та snapshots

Міграція 202610300008_optimistic_queries.sql додає apply_operation, list_snapshot, product_authors_for_ids і приватні operation_receipts. Мутації працюють з правами викликача та чинними RLS/тригерами, перевіряють членство перед повтором, серіалізують однаковий ключ advisory lock і комітять receipt разом зі зміною. Змінений payload з тим самим ключем відхиляється. SHA256 ID залишаються серверними. Повтор повертає актуальний продукт або видалення, не відновлюючи стару картку. Receipt містить SHA256 payload і ID продукту, це додатковий службовий запис без автоматичного очищення. shopik_private не додавати до exposed schemas.

Збереження оновлює змінені поля й різницю тегів. ensure_personal_workspace для наявного простору не пробує INSERT. Авторські поля повертаються лише для результату з перевіркою Workspace, без розширення SELECT профілів. Витрати й суми — один snapshot. Міграцію ще потрібно застосувати до робочого Supabase; SQL/RLS локально перевірені в PGlite. Конкуренція окремих hosted PostgreSQL-з'єднань не перевірялася.

## Задача 011 — авторство та виключення учасника (31.10.2026)

Погоджені правила: завершення покупки доступне всім чинним учасникам; редагування/видалення продукту й категорії — лише автору. Створювати й використовувати категорії можуть усі учасники. При виключенні видаляються продукти учасника, його порожні категорії, а категорії з чужими продуктами передаються власнику без переміщення продуктів. Витрати залишаються незалежними знімками автора/тегів/категорії/суми/дати. Архівні витрати звичайним клієнтом не видаляються.

Застосовувати лише нову `supabase/migrations/202610310010_shared_permissions.sql` після попередніх 001–009. Не повторювати старі міграції. Потім виконати весь `supabase/tests/shared_permissions.sql` у тестовому проєкті (ROLLBACK) та перевірити запуск застосунку. `expenses.product_id` збережений як історичний SHA256 ID без FK на живий продукт; видалення звичайної покупки прибирає витрату через тригер, спеціальне виключення попередньо архівує її. Публічні запис/видалення expenses і зміна членства не надані. Міграція не створює інвайтів чи нових членств.

WorkspaceMembers у налаштуваннях показує публічні display-поля учасників без email/довільного читання профілів, дозволяє власнику виключення й надає вибір між чинними членствами через перевірену HttpOnly cookie. remove RPC перевіряє власника, очікувану дату вступу, блокує Workspace до завершення транзакції, зберігає історію та відкликає членство атомарно. QueryCache й IndexedDB очищають відкликаний scope; created_at членства є епохою відновлення кешу/чернеток після повторного вступу. Метадані перевіряються при поверненні/online та кожні 30 секунд видимого екрана; Realtime й повний офлайн залишаються наступними етапами.

Hosted Supabase не змінювався. Актуальний звіт і межі приймання: `docs/testing/011/README.md`; попередні описи широких прав, каскаду витрат і майбутнього статусу 011 вище є історичними та замінені цим розділом.
