# 014 — Додаткові теми та візуальні правки

## Статус і мета

Реалізовано в коді 31.10.2026; hosted SQL і повний авторизований сценарій залишаються неперевіреними. Звіт, скріншоти й результати перевірок — `docs/design/015/README.md`. Додати чотири колірні теми, ущільнити налаштування, виправити фокус полів, розділити картки продуктів і покращити статистику витрат. Ця задача уточнює оформлення після 012–013 та правок із `docs/design/014/README.md`; вимога окремих карток замінює попереднє рішення про спільну поверхню рядків.

## Результат огляду проєкту

- Прочитано кореневий і вкладений AGENTS.md, README застосунку, PRODUCT, ARCHITECTURE, DATABASE, SUPABASE, задачі 007, 012–013 та звіти дизайну 012–014. Попередні браузерні звіти переважно перевіряли ізольовані компоненти, а не повний авторизований сценарій.
- У `shopik-app/app/globals.css` уже є порожні селектори `pink`, `light-blue`, `light-green`, `light-pink`. На момент огляду файл має незакомічену зміну користувача: додано блок `light-pink`. Зберегти її та працювати поверх актуального файла.
- `lib/theme.ts`, ThemePicker, ThemeToggle, серверна saveTheme і CHECK поля `profiles.theme` підтримують тільки `light`/`dark`. RootLayout та ThemePicker передають назву теми безпосередньо в CSS color-scheme, що потребує окремого зіставлення для нових назв.
- SettingsPanel розміщує всі секції вертикально. ProductList обгортає OrderCard у спільну `.product-rows`; ці ж класи використовує історія витрат. Загальний фокус має `outline-offset: 3px`, а діалог додає ще й box-shadow.
- Статистика вже реалізована в ExpenseChart/ExpenseList через Recharts. Центр, категорії та історія беруть один серверний snapshot; цей контракт потрібно зберегти.

## 1. Додаткові колірні теми

Зберегти `light` і `dark`, додати до явного вибору:

| ID            | Назва           | Оформлення                                                             |
| ------------- | --------------- | ---------------------------------------------------------------------- |
| `pink`        | Рожева          | Загальна світло-рожева палітра: фон, поверхні, поля, акценти та кнопки |
| `light-blue`  | Світла блакитна | Світлі нейтральні поверхні, блакитні/сині акценти та кнопки            |
| `light-green` | Світла зелена   | Світлі нейтральні поверхні, зелені акценти та кнопки                   |
| `light-pink`  | Світла рожева   | Світлі нейтральні поверхні, рожеві акценти та кнопки                   |

- Заповнити підготовлені CSS-блоки семантичними токенами, включно з акцентом, текстом на ньому, кнопками, посиланнями, межами й фокусом. Перевірити каскад пізніших `:root` і глобальних hover-правил, щоб вони не повертали помаранчеві або нейтральні кнопки замість кольору теми.
- Червоні небезпечні кнопки й повідомлення зберігають червону семантику в усіх станах. Власні кольори тегів і стабільні кольори історичних категорій не перефарбовуються під тему.
- Розширити єдиний тип/allowlist тем, вибір у налаштуваннях, тексти валідації, серверне читання та збереження. CSS color-scheme має бути `dark` лише для `dark`, для решти — `light`; назви нових тем не є значеннями color-scheme.
- Узгодити ThemeToggle із шістьма темами: зробити доступний вибір усіх варіантів із хедера, зберігши компактність. При помилці відновлювати точну попередню тему, включно з кольоровою.
- Зберегти негайне застосування, rollback, особистий профіль, HttpOnly cookie, пріоритет профілю після входу, світлий fallback і SSR без спалаху іншої палітри. Вибір у налаштуваннях і хедері має залишатися узгодженим після клієнтської навігації.
- Додати нову міграцію розширення CHECK `profiles.theme` до шести значень; не переписувати вже застосовану міграцію 007. Зберегти поточні значення, default, self-only RLS і grants. Описати порядок застосування в SUPABASE/DATABASE.

## 2. Сітка налаштувань

- На достатній ширині використати grid із двома рівними колонками: компактні «Акаунт» і «Колірна тема» поруч, великі секції «Теги» та «Категорії» — на всю ширину обох колонок.
- На мобільному — одна колонка. Зберегти логічний DOM/Tab-порядок, заголовки, якорі `#tags`/`#categories`, назву Workspace, logout, CRUD і незалежні помилки секцій.
- Вирівняти внутрішні відступи, заголовки й форми; уникнути зайвого вертикального простору, обрізання email, довгих назв і переповнення списків.

## 3. Фокус полів

- Для input, textarea та select зробити чітку обводку без видимого проміжку між полем і фокусом, узгоджену з радіусом. Прибрати конфлікт загального outline та кільця діалогу; не змінювати геометрію поля при фокусі.
- Перевірити форми продукту, тегів, категорій і фільтри витрат. Зберегти видимий клавіатурний фокус інших інтерактивних елементів і розпізнавання помилки поля.

## 4. Окремі картки продуктів

- На `/` кожен продукт має власну поверхню, рамку, радіус і позитивний проміжок до сусіднього. Контейнер не має створювати враження одного суцільного блоку.
- Узгодити звичайні та `.product-today` картки: відсутні негативні відступи, злипання, накладання рамок або обрізані тіні/меню. Зберегти виділення сьогоднішніх покупок.
- Зберегти автора, дату, опис, теги, ціну, меню, завершення, діалоги та pending-стани. Через спільні класи окремо перевірити історію витрат і за потреби обмежити нові правила списком активних продуктів.

## 5. Статистика витрат

- У межах наявної `/expenses` покращити ієрархію місячного підсумку: зрозумілий період і UAH, виразна сума, збалансовані графік і категорії, охайні відступи та вирівнювання сум.
- На широкому екрані графік і легенда можуть бути поруч, на вузькому — послідовно. Велика сума в центрі не перекриває кільце; довгі назви, багато категорій і суми не виходять за межі секції. Текстові підсумки доступні без hover.
- Передбачити порожній місяць, нульові суми, одну/багато категорій, завантаження та помилку. Якщо додавати частки, коректно обробити нульовий знаменник.
- Зберегти єдині Workspace, місяць/рік, AND-фільтр тегів і snapshot для діаграми, суми, легенди та списку; історичні суми, стабільність кольорів і межі `Europe/Kyiv`. Не додавати вигадані метрики, нові запити чи бібліотеку графіків для оформлення.

## Реалізація та приймання

- Використовувати TypeScript і наявні залежності; залишати змістовні коментарі до змінених компонентів, HTML/JSX-секцій та функцій. Перед кодом прочитати релевантні посібники встановленого Next.js у `shopik-app/node_modules/next/dist/docs/`.
- Зміни схеми обмежити допустимими темами. Зберегти серверні перевірки доступу, бізнес-правила, SHA256 ID продуктів і поточну Google/Supabase-авторизацію.
- Перевірити всі шість тем на `/`, `/settings`, `/expenses`, `/login` та в діалогах; hover, active, disabled, focus, error і destructive. Контраст звичайного тексту від 4.5:1, значущих меж/фокуса від 3:1, зони іконкових дій від 44 × 44 px.
- Браузерні ширини: 360, 390, 768, 1440 CSS px. Немає горизонтального переповнення, картки розділені, сітка адаптивна, фокус прилягає до поля; доступні клавіатура, Escape та повернення фокуса меню/діалогів. Враховано reduced-motion.
- Оновити unit-тести allowlist, fallback, профілю/cookie та зіставлення color-scheme; перевірити rollback кольорової теми. SQL-тести: нові значення приймаються, невідомі відхиляються, ізоляція акаунтів збережена.
- Запустити в `shopik-app`: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` (за відомої помилки PostCSS worker — `npm run build -- --webpack`). SQL і реальне збереження теми перевірити за наявності доступу; відсутність доступу явно вказати, не підміняти перевірку заглушкою.
- Зберегти порівняльні скріншоти й звіт у новій теці `docs/design/015/`, щоб не перезаписати наявні матеріали `014`. Оновити PRODUCT/ARCHITECTURE/DATABASE/SUPABASE за фактичним результатом. Незавершені перевірки 013 не вважати автоматично пройденими.
