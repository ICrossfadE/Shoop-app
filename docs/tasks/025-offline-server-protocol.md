# 025 — Серверний протокол: ревізії, повтори та дата офлайн-покупки

Статус: Заплановано. Пріоритет: P0. Залежності: [020](020-mobile-feasibility.md), [021](021-shared-mobile-contracts.md).
Батьківський план: [Android plan](../MOBILE_ANDROID_PLAN.md). Пов'язана задача: [010B](010-offline-sync.md).

## Мета

Надати мобільному клієнту вузький користувацький RPC-протокол із захистом від застарілого запису, дублювання та відправлення черги колишнього членства.

## Роботи

- Спочатку перевірити фактичні RPC/RLS і міграції 001–016 на тестовій копії. Додавати нові міграції; старі й production-дані не переписувати.
- Запровадити серверні ревізії для змінюваних сутностей/зв'язків. Зміна лише тегів, старі вебоперації, прямі дозволені Data API writes і видалення тегу теж мають змінювати відповідні ревізії.
- Додати версіоновані RPC із expected revision, operation ID, незмінним payload, receipts та expected membership epoch. Поточне членство й epoch перевіряти перед прийняттям/повтором; rejoin не робить стару чергу чинною.
- Підтримати створення/перейменування/видалення категорій, створення/видалення тегів, товарні дії, пакетне завершення й корекцію фактичної суми. UUID довідників і SHA256 товарів генеруються сервером; відповідь повертає підтверджені ID, ревізії та стан.
- Для конфлікту повертати безпечний актуальний стан або статус deleted/completed/inaccessible. Відсутня сутність не повинна автоматично відновлюватися.
- Використати погоджені у 020 правила occurred_at; зберігати час синхронізації окремо, перевіряти дату сервером. Не дозволити клієнту довільно переписувати історичні дати, план, автора чи архів.
- Забезпечити атомарність пакета до 500 товарів, грошові межі, OR-фільтри, незмінний planned_amount і історію тегів. Зберегти чинний онлайн-контракт для вебу; не видавати mobile service_role.
- Визначити повне читання поточного списку/каталогу та відомих місяців із консистентними ревізіями. Для v1 повні snapshots допустимі; складний delta-протокол не обов'язковий.

## Критерії готовності

- Повтор після commit без відповіді не створює другу сутність/витрату. Змінений payload із тим самим ключем відхиляється.
- Два пристрої не перезаписують один одного мовчки; tag-only зміна виявляється.
- Виключення та повторний вступ блокують старі epoch-операції; сторонній акаунт і anon доступу не мають.
- Покупка до місячної межі після прийнятої сервером синхронізації потрапляє до належного Kyiv-періоду.
- Старий вебклієнт працює з новою схемою й оновлює ревізії. Є порядок розгортання та сумісність версій APK.

## Перевірки

SQL/RLS, сценарії переходу заповненої схеми, повтори й незмінні receipts, конфлікти категорій/тегів/покупок, time validation, межі Kyiv/DST та архів. Справжню конкурентність перевірити на незалежних PostgreSQL-з'єднаннях; PGlite сам по собі цього не доводить. Звіт: `docs/testing/025-offline-protocol/`.
