# 010 — Локальні дані та офлайн-синхронізація

## Статус і залежності

У роботі з 31.10.2026 після 008 і 009. Почато етап 010A: постійний кеш завантажених списків і локальні чернетки продуктів. Не є умовою миттєвого відгуку. Перед реалізацією погодити правила конфліктів і виходу з незбереженими змінами. Для спільних просторів врахувати серверні права й архів витрат із 011.

## Обсяг

- Зберігати доступні списки й чергу локальних операцій в IndexedDB, окремо за акаунтом і Workspace. Не копіювати токени авторизації у власну чергу.
- Дозволити роботу з раніше завантаженими даними без мережі. Показувати «Без інтернету», кількість незбережених змін, помилку та можливість повторити синхронізацію.
- При наявності мережі відправляти зміни одразу; при відновленні з'єднання, відкритті застосунку та відновленні чинної сесії продовжувати чергу. Не покладатися лише на login, logout або закриття вкладки.
- Кожна операція має стійкий унікальний ключ; сервер гарантує ідемпотентність повтору після втрати відповіді, перезавантаження чи паралельного запуску вкладок. Збережені ID продуктів відповідають вимозі SHA256.
- Зберігати порядок залежних операцій: категорія/тег перед продуктом, створення продукту перед зміною чи завершенням. Передбачити міграцію формату локального сховища.
- Supabase залишається джерелом підтверджених даних. Перевіряти права для кожної відкладеної операції, не довіряти локальним ролям або датам.
- Визначити версії записів або інший контроль конкурентних змін. Видалені, завершені чи недоступні після виключення записи не відновлюються застарілою чергою.
- Не повторювати безкінечно відмову доступу чи валідації. Відрізняти тимчасову мережеву помилку від конфлікту та остаточної відмови.
- Logout і зміна акаунта не повинні передавати чергу іншому користувачу. Правило збереження або очищення незавершеної черги визначити до реалізації; не приховувати втрату незбережених дій.

## Питання перед реалізацією

- Як показувати й розв'язувати конфлікт між локальною зміною та новішим станом сервера?
- Що робити з чергою при добровільному logout: дочекатися синхронізації, залишити ізольованою до наступного входу чи видалити з явним підтвердженням?
- Який обсяг і строк зберігання приватних даних на пристрої прийнятні?

## Перевірки та критерії готовності

- Перевірити офлайн → перезавантаження → онлайн, прострочення сесії, втрату відповіді, кілька вкладок, зміну акаунта та виключення з Workspace.
- Повтори не дублюють продукти/витрати; конфлікт не перезаписує підтверджені дані мовчки.
- Виконати lint, typecheck, тести черги й ідемпотентності, SQL/RLS-тести та браузерні сценарії з нестабільною мережею.

## Послідовність реалізації після огляду 31.10.2026

### 010A — постійний кеш і чернетки (поточний етап)

- Нативний IndexedDB, версія схеми 1, без нових залежностей. Зберігаються лише підтверджені query snapshots та серіалізовані поля чернетки продукту, без DOM, credentials і promises.
- Ключі містять акаунт, Workspace і точний фільтр. Серверний bootstrap має пріоритет; локально відновлені дані вважаються застарілими й перевіряються мережею. Відсутній snapshot не означає порожній список.
- Чернетка відновлюється за явною кнопкою після повторного відкриття форми цього продукту (або нового продукту в тому самому Workspace). Зберігаються operationId і прапорець невідомого результату для ручного повтору незмінного запиту. Автовідправлення відсутнє.
- Тимчасова політика першого етапу: записи придатні до відновлення 7 діб; прострочені видаляються при записах. Logout, зміна акаунта й виявлена відмова доступу очищають дані попереднього акаунта. Явне скасування форми або успішне збереження видаляє її чернетку. Остаточна політика retention потребує погодження до 010B.
- Показувати стан без мережі та помилку локального збереження; застосунок має продовжувати онлайн-роботу, якщо IndexedDB недоступний.
- Це не офлайн-запуск після закриття: прямі URL й reload усе ще потребують серверного bootstrap. Каталог категорій/тегів поки береться з наявної оболонки/сервера. Чернетки тегів і категорій ще не зберігаються.

### 010B — черга офлайн-операцій (не розпочата)

Перед кодом погодити конфлікти, logout із чергою, строк зберігання та дату офлайн-покупки. Додати серверну ревізію, що змінюється також при зміні лише тегів; порівнювати очікувану ревізію атомарно. Не плутати ідемпотентність із захистом від конкурентного перезапису. Перевірити фактичне застосування міграції 008.

Черга повинна зберігатися до підтвердження локального прийняття зміни, мати стани pending/sending/needs-auth/conflict/rejected, керувати повтором і кількома вкладками. Залежності локальних сутностей переводяться в серверні ID перед фіксацією незмінного payload операції. Серверні SHA256 ID продуктів зберігаються. Початковий обсяг — продукти в наявних категоріях; нові офлайн-категорії/теги окремим розширенням.

Окремо визначити occurred_at: зараз тригер бере час серверної синхронізації, тому завершення 31 жовтня з підключенням 1 листопада переносить витрату в інший місяць. Локальний час не приймати без серверних правил перевірки. Прострочена сесія призупиняє чергу; підтверджене відкликання членства відхиляє операції.

### 010C — запуск без мережі (не розпочатий)

Service worker і версіонована публічна оболонка, відновлення довідників та локальних даних після закриття. Не кешувати приватний SSR HTML спільним HTTP-кешем. Продумати оновлення оболонки/локальної схеми й сумісність черги з новим деплоєм. Background Sync — додаткове покращення, основна синхронізація працює у відкритому застосунку.
