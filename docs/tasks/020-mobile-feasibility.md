# 020 — Android: технічний прототип і контракт першої версії

Статус: У роботі — ізольований прототип створено; Android-приймання очікує JDK/SDK. Пріоритет: P0. Залежності: немає.
Батьківський план: [Android plan](../MOBILE_ANDROID_PLAN.md).

Початок реалізації 05.11.2026: [код та команди](../../shopik-mobile/README.md),
[результати перевірок](../testing/020-mobile-feasibility/README.md).
Поточний обсяг — Android; iOS виключено. Готовність 020 ще не підтверджено.

## Мета

До перенесення основного UI підтвердити шлях React/TypeScript + Capacitor з локальними assets, Supabase, повним погодженим офлайн-сценарієм і можливістю майбутнього iOS.

## Роботи

1. Прочитати актуальні офіційні інструкції Capacitor, Android environment setup, Supabase OAuth/PKCE. Перед змінами Next.js читати встановлену документацію `shopik-app/node_modules/next/dist/docs/` за `AGENTS.md`.
2. Перевірити фактичні Node/JDK/SDK/Android Studio, пристрій/емулятор та WebView; зафіксувати сумісні версії, minimum/target SDK. Відсутність `java`/`adb` у PATH сама по собі не означає відсутність SDK.
3. Мінімальним ізольованим прототипом перевірити локальний холодний запуск, IndexedDB після force stop/reboot/update, dialog/popover, доступ до Supabase та OAuth через системний браузер. Прототип створювати лише після початку розробки, не в етапі планування.
4. Вибрати сховище за результатами: IndexedDB є першим кандидатом; SQLite додавати тільки за доведеної потреби. Окремо підтвердити підтримуваний адаптер credentials до Keystore/Keychain.
5. Зафіксувати application ID, domain/callback, контракти адаптерів, локальні ID → серверні ID, епохи членства, версію протоколу й міграцію локальних даних.
6. Узгодити точні retention/offline-access правила та серверну перевірку дати офлайн-покупки. Невідправлені зміни не видаляти мовчки за поточним TTL 7 діб. Погоджені користувачем конфлікти й logout не відкривати заново без потреби.
7. Зіставити фактично застосовані hosted-міграції з локальними 001–016, без повторного застосування старих міграцій. Відокремити підтверджені факти від невідомого стану production.

## Критерії готовності

- Є запис архітектурного рішення з результатами прототипу, обраними версіями, сховищем, OAuth і детальними правилами часу/retention.
- Обов'язковий сценарій включає офлайн-створення категорії й тегу; не звужений до товарів у наявних довідниках.
- Видно перелік справді потрібних залежностей і причину кожної; встановлення «про запас» немає.
- Невирішені питання позначені явно. Якщо ключовий прототип не пройдено, скоригувати план до масового перенесення компонентів.

## Перевірки

Холодний старт у режимі польоту після початкового завантаження; запис і відновлення даних після kill/reboot/update; справжній Google-вхід і повернення; базові DOM-функції на мінімальному WebView. Після змін коду — належні lint/typecheck/unit/build. Звіт зберегти в `docs/testing/020-mobile-feasibility/`.
