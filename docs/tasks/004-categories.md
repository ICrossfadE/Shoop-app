# 004 — Категорії та сторінка витрат

## Статус

Код і міграції реалізовані. Застосування міграцій та результати реальних SQL/браузерних перевірок фіксуються окремо.
Ця задача уточнює попередні вимоги: початкову категорію «Обов'язкові покупки» можна редагувати й видаляти за загальними правилами; завершення продукту автоматично додає його до витрат без окремого підтвердження.

## Категорії Workspace

- При створенні Workspace автоматично створюється категорія з назвою «Обов'язкові покупки».
- Користувач може створювати власні категорії та редагувати їхні назви.
- Початкову категорію «Обов'язкові покупки» також можна редагувати або видалити, якщо вона порожня.
- Повторний вхід чи оновлення сторінки не створює дублікати категорій і не відновлює навмисно видалену початкову категорію.
- Перемикання категорії показує лише продукти, які до неї належать, у поточному Workspace.
- Для кожної категорії передбачені завантаження, порожній список, помилка й повторне завантаження.
- Якщо категорій немає, інтерфейс пропонує створити першу категорію; створення продукту недоступне.

## Продукти та категорії

- Кожен продукт належить одній категорії свого Workspace.
- У формі створення продукту обов'язкове поле вибору категорії; під час редагування можна змінити категорію.
- Без категорії створити продукт не можна: правило перевіряється формою, сервером і базою.
- Категорію не можна видалити, якщо вона містить хоча б один продукт; заборона має діяти і для прямих запитів до Supabase, і при конкурентному створенні продукту.
- Видалення категорії не повинно каскадно видаляти продукти.
- Видалення продукту саме по собі не завершує його й не додає до витрат.
- Перед видаленням запропонувати через модальне вікно чи повинно воно потріпити у ввитрати або всетаки видалити.

## Сторінка «Витрати»

- Окрема сторінка/пункт навігації збирає завершені продукти поточного Workspace автоматично.
- Продукт будь-якої категорії потрапляє на сторінку "витрати" після завершення;
- Перейменування або видалення початкової порожньої категорії не прибирає сторінку статистики.
- На сторінці показуються завершені покупки за обраний календарний місяць і рік, перелік їхніх категорій, сума за кожною категорією та загальна сума всіх покупок цього місяця в UAH.
- Місяць визначається датою здійснення витрати, початково — датою завершення продукту. Дата створення активного продукту на групування не впливає.
- Дані різних років і Workspace не змішуються. Для місяця без витрат показуються нульова сума та порожній стан.
- Повторна доставка запиту завершення не повинна дублювати витрату або збільшувати суму повторно.
- Запис зберігає знімок назви, суми, валюти й категорії на момент завершення; подальше редагування продукту не переписує історичну статистику.

## Запропонована технічна схема

Схема реалізована новими міграціями відповідно до погоджених нижче правил історії.

- `categories`: `id`, `workspace_id`, `name`, `created_by`, `created_at`, `updated_at`; складений унікальний ключ `(workspace_id, id)`.
- `products.category_id`: обов'язкове посилання через `(workspace_id, category_id)` на категорію того самого Workspace, `ON DELETE RESTRICT`.
- `expenses`: окремий запис фактичної покупки з `workspace_id`, посиланням на продукт, знімком назви, суми, валюти та категорії, датою здійснення. Видалення продукту каскадно видаляє витрату.
- Створення Workspace й початкової категорії відбувається атомарно. Для вже наявних Workspace — одноразове заповнення категорії та прив'язка існуючих продуктів без видалення даних; це не імпорт старого демонстраційного JSON.
- Перехід продукту в `completed` і запис витрати мають бути атомарними; захист від дублювання реалізується в базі.
- RLS дозволяє операції з категоріями, продуктами й витратами лише учасникам відповідного Workspace; клієнт не може підмінити автора чи Workspace.
- Агрегація статистики застосовує той самий контроль доступу. Клієнт не передає довільний user ID як джерело повноважень.

## Погоджені правила історії та часу — 29.10.2026

1. Видалення завершеного продукту прибирає пов'язану витрату й перераховує статистику.
2. Повернення в активні прибирає витрату. Наступне завершення додає новий знімок з актуальною ціною, категорією та новою датою. Повтор запиту `completed` без повернення в активні нічого не дублює.
3. Межі місяця визначаються за `Europe/Kyiv`, включно з переходами літнього/зимового часу та роком.
4. Перед видаленням «Перенести у витрати» означає завершити й залишити продукт; «Видалити» прибирає продукт і його витрату. Уже завершений продукт можна залишити у витратах без дублювання.

## Запуск і перевірки

Застосувати окремо й послідовно лише нові міграції:
1. `supabase/migrations/202610290003_categories.sql`.
2. `supabase/migrations/202610290004_expenses.sql`.

Наявні продукти зберігаються й отримують початкову категорію. Для вже завершених продуктів міграція записує витрату за останньою відомою датою `updated_at`, оскільки раніше окрема дата завершення не зберігалась.

SQL-тест: `supabase/tests/categories_expenses.sql`. Запускати весь файл після обох міграцій; тестові користувачі й дані відкочуються. Очікуваний результат: `PASS: categories, expense lifecycle, Kyiv months and RLS`.

Автоматично: `npm test`, `npm run lint`, `npm run typecheck`, `npm run build -- --webpack`, `npm run test:smoke`, `npm run test:supabase`.

Браузерний сценарій: створити й перейменувати категорію; створити в ній продукт; перемкнути категорії; спробувати видалити непорожню; завершити продукт; перевірити `/expenses`; змінити його ціну й перевірити незмінність знімка; повернути в активні й перевірити зменшення суми; завершити знову; видалити й перевірити суму. Видалити всі порожні категорії, оновити сторінку та перевірити, що додавання продукту недоступне, а початкова категорія не відновилася.

## Результати перевірки — 29.10.2026

- Пройшли 14 локальних тестів, lint, TypeScript та production build через Webpack.
- `test:supabase` підтвердив існування categories/expenses і заборону анонімного читання та виклику місячної статистики.
- `test:smoke` підтвердив захист `/` і `/expenses` без сесії та з пошкодженими/підробленими cookie, а також попередні OAuth-сценарії.
- Користувач повідомив успішне застосування нових міграцій: `Success. No rows returned`.

- Авторизований браузерний сценарій категорій/витрат агентом окремо не перевірений; його не позначено пройденим.

## Критерії приймання

1. Новий Workspace одразу має одну початкову категорію «Обов'язкові покупки», без дублікатів після повторного входу.
2. Порожню категорію, включно з початковою, можна перейменувати й видалити.
3. Перемикання категорій змінює список; дані іншого Workspace недоступні.
4. Без категорій неможливо створити продукт, включно з прямим запитом до бази.
5. Вибрана категорія зберігається після створення, редагування й перезавантаження сторінки.
6. Видалення категорії з продуктами заборонене на рівні бази; продукти залишаються цілими.
7. Завершений продукт автоматично з'являється на сторінці витрат; видалення активного продукту нічого туди не додає.
8. Повторний запит завершення не подвоює статистику.
9. Місячні загальна сума та суми за категоріями правильні на межі місяців і років; порожній місяць дає нуль.
10. SQL-тести покривають RLS двох користувачів, зовнішні ключі, заборону видалення непорожньої категорії та атомарність завершення.
11. Пройдені lint, TypeScript, тести бізнес-правил, production build і браузерні сценарії категорій та витрат.

## Порядок реалізації

1. Уточнити правила історії, повторного завершення та часового поясу.
2. Додати міграції категорій, обов'язкового зв'язку продукту, витрат і RLS; зберегти наявні дані.
3. Реалізувати керування категоріями, перемикання списку та поле категорії у формі продукту.
4. Додати атомарне завершення з обліком витрати та сторінку місячної статистики.
5. Запустити SQL, автоматичні й браузерні перевірки; оновити документацію результатів.
