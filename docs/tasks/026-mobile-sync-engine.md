# 026 — Автосинхронізація залежної черги й конфлікти

Статус: Заплановано. Пріоритет: P0. Залежності: [023](023-mobile-authentication.md), [024](024-mobile-local-repository.md), [025](025-offline-server-protocol.md).
Батьківський план: [Android plan](../MOBILE_ANDROID_PLAN.md).

## Мета

Відправляти локально прийняті дії одразу за наявності мережі або після відновлення, із захистом від втрат, дублів та мовчазного конфліктного перезапису.

## Роботи

- Реалізувати єдиний coordinator на активний scope; lock/lease із відновленням після process death. Паралельні resume/network/auth події не запускають дубль воркера.
- Дотримуватись залежностей категорія/тег → товар → зміни/завершення/корекція. Pending-зміни одного товару мають правильну базову ревізію після попереднього ack.
- Після першого відправлення незмінні payload/ID; при timeout повторювати ту саму операцію. Не підміняти невизначений запит новим і не об'єднувати вже відправлені дії.
- Розділити transport retry з backoff, needs-auth, conflict та final rejection. Наявність мережі — підказка, реальна відповідь вирішує результат. Не повторювати відмови прав/валідації нескінченно.
- Розв'язувати локальні refs і атомарно записувати ack/mapping. Якщо сервер створив сутність, а процес загинув до локального ack, повтор відновлює початковий результат.
- Реалізувати погоджений користувачем вибір локальної/серверної версії. Для дубля категорії/тегу запропонувати вибір наявної сутності або іншу назву; залежні дії чекають рішення.
- Врахувати серверне видалення/завершення, втрату членства, повторний вступ, scope switch і пізню відповідь старого акаунта. Невідправлене коригування витрати не створює другу витрату.
- Після синхронізації перечитати confirmed state й заново застосувати ще pending projection; мережевий snapshot не стирає локальних намірів.

## Критерії готовності

- Ланцюг нова категорія + тег + товар + завершення синхронізується без дублів після рестарту на кожному кроці.
- Відправлення працює під час активної роботи, після online/resume/відновлення auth; закриття програми не є єдиною точкою sync.
- Конфлікт блокує залежні операції, але не весь незалежний список. Вибір користувача зберігається й переживає рестарт.
- Немає втрати локальної черги при expiry токена, тимчасовому timeout, оновленні програми чи metadata refresh.

## Перевірки

Модельні тести порядку/повторів плюс інтеграція реального local store/RPC: kill до/після server commit і local ack, flaky network, подвійний worker, два пристрої, tag-only conflict, duplicate names, eviction/rejoin. Звіт: `docs/testing/026-sync-engine/`.
