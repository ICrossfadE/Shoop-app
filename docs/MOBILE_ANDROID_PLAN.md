# Shopik на Android — огляд, рішення та план

Дата: 05.11.2026. Статус: код 021–024 реалізовано; debug APK зібрано; апаратне приймання 020/022 та реальний Google OAuth 023 відкриті.

Оновлені вказівки користувача: повний офлайн потрібен лише в Android-додатку; iOS та задача 030 виключені з виконання. Вигляд і поведінку вебзастосунку зберегти. Робота ізольована в гілці `feat/android-offline-restart`: Android у `shopik-mobile/`, спільне ядро у `shopik-app/lib/domain/`. У вебі збережено сумісні імпорти й правила, палітри перенесено без зміни значень; SQL і зовнішні сервіси не змінено. Задачі нижче не є запущеними агентами.

Поточний результат: спільні моделі/контракти, три екрани оболонки, маршрутизація/Back, шість тем, lifecycle і транзакційний тест сховища. Додано код Android Google PKCE/Keystore та scope gate; зовнішній OAuth allowlist потребує налаштування. Це ще не повний Android-застосунок. [023](testing/023-mobile-auth/README.md), [020](testing/020-mobile-feasibility/README.md), [021](testing/021-shared-mobile-contracts/README.md), [022](testing/022-mobile-shell/README.md), [команди APK](../shopik-mobile/README.md). JDK 21 та Android SDK 36 встановлено; [debug APK і звіт 024](testing/024-local-repository/README.md) готові. Локальний репозиторій/outbox перевірено Node-тестами та справжнім Chromium IndexedDB; force stop/reboot/update на Android ще не перевірено. За прямою наступною вказівкою користувача кодову частину продовжено, але апаратні критерії 020/022 не видаються за пройдені.

## 1. Погоджені вимоги

- Пріоритет — Android. Перший результат — підписаний release APK для ручного встановлення, без обов'язкової публікації в Google Play.
- Після першого успішного онлайн-входу та завантаження простору потрібні запуск без мережі, перегляд і зміни даних з подальшою синхронізацією.
- Офлайн потрібні **нові категорії та теги**, а також створення, редагування, видалення й завершення товарів. Початкове обмеження лише на вже завантажені категорії відхилено користувачем.
- Конфлікт показує локальну та серверну версії; користувач обирає дію. Автоматично перезаписувати новіші серверні дані не можна.
- При добровільному виході з невідправленими змінами запропонувати синхронізацію або явне видалення; також можна скасувати вихід. У режимі без мережі синхронізація очікує підключення.
- Push-сповіщення не обов'язкові. iOS бажаний, але не блокує Android.

## 2. Результат огляду репозиторію

Огляд охопив структуру всього репозиторію, модулі клієнта й сервера, конфігурацію, бізнес-модель, SQL-міграції, наявні перевірки та документацію попередніх етапів. Це архітектурний огляд для мобільного плану, а не твердження про повний аудит безпеки чи проходження сценаріїв на телефонах. Згенеровані `.next/`, `node_modules/`, приватні значення `.env.local` і Git-об'єкти не є вихідним кодом для перенесення.

### Критичні відмінності від готового офлайн-застосунку

1. [010A](testing/010/README.md) — кеш і чернетки. [010B/010C](tasks/010-offline-sync.md) ще не реалізовані. Service worker, manifest і нативної оболонки в поточному коді немає.
2. Ідемпотентність receipts захищає повтор тієї самої операції, але звичайне редагування ще не має повного протоколу перевірки серверної ревізії. Зміна лише тегів теж повинна змінювати ревізію товару.
3. `sync_product_expense()` ставить `clock_timestamp()` під час серверного запису. Офлайн-покупка до межі місяця при синхронізації наступного місяця зараз отримає інший звітний період.
4. Поточне очищення всього локального кешу при перемиканні простору або logout непридатне для майбутньої невідправленої черги без погодженого UX.
5. UUID операції, локальний тимчасовий ключ і постійний SHA256 ID товару — різні ідентичності. Потрібне стійке зіставлення, а не запис тимчасового UUID у серверне поле продукту.
6. Онлайн-відкликання доступу неможливо миттєво виявити на відключеному телефоні. Офлайн-копія має явно визначений строк доступності; при відновленні зв'язку перевірити членство перед відправленням.

## 3. Рекомендований шлях

**Окремий React + TypeScript клієнт, зібраний Vite і локально упакований Capacitor. Supabase залишається спільним сервером для вебу та смартфона.**

Capacitor використовує Android WebView: UI буде HTML/CSS усередині встановленого застосунку, а не переписаними Android-віджетами. Це відповідає вже готовому мобільному інтерфейсу Shopik і зберігає шлях до iOS. HTML, JavaScript, CSS, шрифти й потрібні іконки включаються в APK, тому відкриття оболонки не залежить від Vercel.

Основні шари: локальний UI → локальний репозиторій і стійка черга → синхронізація → Supabase Auth/RPC/PostgreSQL. Вебверсія зберігає свій Next.js SSR та окремий адаптер. Початковий серверний транспорт мобільного клієнта — наявний `supabase-js` із користувацькою сесією та вузькими RPC/RLS. Новий проміжний REST-сервер для всіх дій не потрібен, якщо перевірка контрактів у 020/025 підтвердить цей шлях.

Приблизна майбутня структура: `shopik-app/` для вебу, `shopik-mobile/` для React/Vite/Capacitor, `packages/` для незалежних TypeScript-моделей та спільного UI, `supabase/` для єдиної серверної моделі. Це пропозиція для задачі 021, зараз ці каталоги не створюються. npm workspaces достатньо; Turborepo/Nx, Ionic UI, Firebase та інший state manager не додаються за замовчуванням.

### Чому не інші варіанти

- **PWA/TWA:** дозволяє використати вебверсію, але для поточного SSR все одно доведеться окремо реалізувати офлайн-запуск і чергу. Для заданого APK з перспективою iOS локально упакований клієнт дає пряміший контроль над запуском і життєвим циклом. [Офіційний опис TWA](https://developer.chrome.com/docs/android/trusted-web-activity).
- **React Native + Expo:** придатний для Android/iOS і Supabase, але HTML-компоненти, CSS, native dialog/popover та Recharts потребуватимуть суттєвого переписування. Повернутися до цього варіанта, якщо з'явиться вимога саме нативного UI, складних віджетів або якщо технічний прототип Capacitor не пройде перевірки. [Документація Expo/Supabase](https://docs.expo.dev/guides/using-supabase/).
- **Kotlin/Swift:** окремі клієнти й більший обсяг переписування, до того ж бізнес-логіка вийде за обрану TypeScript-основу.

Поточний Next.js не можна просто зібрати через `output: 'export'`: проєкт використовує cookies, Proxy, динамічні Route Handlers і Server Actions, які статичний експорт не підтримує. [Обмеження Next.js](https://nextjs.org/docs/app/guides/static-exports#unsupported-features). У production не підставляти URL Vercel у `server.url`: документація Capacitor відносить його до live reload, а така оболонка не вирішує офлайн-запуск. [Конфігурація Capacitor](https://capacitorjs.com/docs/config).

## 4. Обсяг першого APK

### Без мережі після початкової синхронізації

- Холодний запуск, останній доступний простір, списки, категорії, теги, фільтри, відомі учасники та тема.
- Нові категорії й теги; створення товару в локальній категорії з локальними тегами; редагування/видалення активних товарів; одиночне й пакетне завершення до чинного ліміту 500.
- Наявне керування категоріями: перейменування та видалення дозволених порожніх категорій; видалення тегу зі збереженням історичних знімків. Нове редагування назви/кольору тегу не входить у поточний продукт.
- Перегляд завантажених місяців витрат; локальний план/факт/економія, коригування фактичної суми та дозволене видалення неархівної покупки. Невідправлені підсумки позначаються як попередні.
- Успішне локальне прийняття дії означає завершений стійкий запис. Закриття процесу чи перезапуск телефона не втрачають прийняту чергу.
- Незавантажений місяць не відображається як нуль витрат. Перший вхід і перше завантаження простору потребують мережі.

### З мережею

- Google-вхід, відновлення/оновлення сесії, підтвердження актуальних прав та синхронізація.
- Приєднання/запрошення/виключення учасників, відновлення особистого простору, серверне перейменування й перемикання простору. Офлайн-перемикання просторів не є вимогою v1.
- Після повернення з фону та при відновленні мережі — актуалізація каталогу, членства й даних, без стирання невідправлених дій.
- Зміна теми працює локально одразу; особисту серверну тему узгодити окремою простою операцією. Перемикання простору з pending-змінами очікує їх синхронізації або явного відкидання, а не мовчки очищає чергу.

Робота в background не гарантується: базова синхронізація виконується у відкритому застосунку та при поверненні. Push, сканер, камера, віджети, біометрія, платежі та публікація в магазинах не входять до першого APK.

## 5. Правила даних і синхронізації

1. Окремо зберігати підтверджений серверний стан, локальні наміри/чернетки та чергу. Офлайн-модель містить сутності та зв'язки, а не лише snapshots точних фільтрів.
2. Ізоляція за акаунтом, простором і перевіреною епохою членства. Старі дії після виключення та повторного вступу не повинні отримати новий доступ автоматично.
3. Послідовність залежностей: створити категорію/тег → зіставити серверні ID → створити товар → зіставити SHA256 ID → змінити/завершити товар. Після отримання відповіді зіставлення, стан сутності й підтвердження черги фіксуються локально атомарно.
4. Після початку відправлення operation ID та серверний payload незмінні. Втрата відповіді повторює той самий запит. Новий користувацький вибір після конфлікту є новою операцією з новою очікуваною ревізією.
5. Сервер перевіряє ревізії, членство, автора де потрібно, архівність і допустимий час покупки атомарно. Не приймати клієнтську роль як право доступу.
6. Всі допустимі шляхи серверного запису, включно зі старою вебверсією та зміною лише тегів, мають оновлювати ревізії. Інакше мобільний контроль конфліктів буде неповним.
7. Постійні ID продуктів залишаються серверними SHA256. Хешування ID не є шифруванням даних. Паролів не додаємо: Google/Supabase залишаються способом входу.
8. Credentials не потрапляють у чергу, snapshots, логи або інвайт-посилання. Сесія — в окремому адаптері з опорою на Android Keystore / iOS Keychain; вибір підтримуваного механізму перевірити в 020/023. Не вважати звичайний Capacitor Preferences захищеним сховищем токенів.
9. Помилка диска/квоти не може закінчитись повідомленням «збережено». Для незавершених дій не застосовувати поточне автоматичне очищення через 7 діб.
10. Дублі назв категорій/тегів на різних пристроях — явний конфлікт із вибором наявної сутності або іншої назви; не зливати їх мовчки.

### Деталі, які треба закрити в першій задачі

- Точний строк зберігання приватної офлайн-копії та доступ після довгої відсутності перевірки сесії. Рекомендація: не видаляти невідправлені дії за TTL; строк confirmed-кешу й правила доступу підтвердити окремо.
- Валідація часу офлайн-покупки, похибки годинника, старих дат і зміни місяця. Рекомендація: зберігати час дії та час синхронізації окремо, групувати за прийнятим сервером часом покупки в `Europe/Kyiv`; неприйнятний час показувати як конфлікт для виправлення.
- Конкретний мінімальний Android/WebView і вимоги SDK/JDK. `java` та `adb` не знайдені в поточному PATH; це не доводить відсутність установленого Android Studio/SDK.
- Стабільні application ID, канонічний HTTPS-домен інвайтів та callback. Приклади в майбутніх документах не вважати реальними production-налаштуваннями.
- IndexedDB за наявним досвідом — перший кандидат для даних. На Android перевірити стійкість, квоти й транзакції; якщо перевірки не пройдені, обрати SQLite через обґрунтований адаптер. Не встановлювати обидва механізми наперед.

Ці пункти не блокують складання плану; вони входять до критеріїв готовності 020 і мають бути вирішені перед залежними змінами.

## 7. Ознака готовності першої версії

На фізичному Android установити release APK, увійти онлайн, синхронізувати простір, вимкнути мережу, створити категорію, тег і товар у них, змінити його та завершити покупку. Примусово закрити застосунок і перезапустити телефон: дані й черга збережені. Повернути мережу: на другому пристрої/у вебі з'являється рівно один комплект сутностей і одна витрата з правильною датою, планом та сумою. Конфлікт, втрачена відповідь, вихід із чергою, виключення та повторний вступ перевірені окремо. Оновлення APK тим самим підписом зберігає локальні дані й чергу.

## 8. iOS

Capacitor дозволяє використати той самий React-клієнт на iOS. Для реальної збірки потрібні macOS/Xcode локально або на macOS CI, належне підписування та тестування WKWebView. На поточній Windows-машині локальний iOS build не виконується. Інсталяція на iPhone має окремі правила підписування/поширення й не повторює APK-сценарій Android. [Офіційний iOS setup](https://capacitorjs.com/docs/ios).
