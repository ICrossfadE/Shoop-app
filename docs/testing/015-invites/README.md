# 015 — перевірка запрошень через посилання

Дата: 31.10.2026. Реалізація готова в коді; hosted Supabase і справжній Google OAuth не змінювалися та не перевірялися.

## Поведінка

Власник поточного простору створює одноразове посилання в налаштуваннях учасників, копіює його й може відкликати. Строк дії — 7 діб. Після Google Login одержувач бачить простір, власника та власний поточний акаунт і явно погоджується на вступ. Нове членство має роль member; особисті дані не об'єднуються. Чинний учасник відкриває простір без витрачання посилання.

Секрет складається з 32 випадкових байтів, передається у fragment і показується власнику лише один раз. База зберігає SHA256. Повтор створення з тим самим operation_id повертає метадані без нового секрету; після втраченої відповіді потрібний рядок позначений «Ваш останній запит» для відкликання. Reload не відновлює секрет.

Fragment стирається з адреси. Контекст переходить у HttpOnly/SameSite=Lax cookie з path=/invite на 30 хвилин, Secure у production. Токен не зберігається у QueryCache/IndexedDB. До входу немає lookup метаданих; preview і acceptance виконуються окремими authenticated POST/RPC. GET не додає членства. Закінчений сценарій і недійсні контексти очищають cookie. OAuth використовує тільки фіксоване продовження flow=invite → /invite, без довільного next.

Прийняття, відкликання та виключення мають спільне блокування Workspace у PostgreSQL. Повтор прийняття дозволений лише тому самому акаунту з тією самою епохою членства. Після виключення старі використані й старі pending-посилання не повертають доступ; нове запрошення створює нову епоху. Відкликання вже прийнятого посилання не виключає учасника.

Ліміти на акаунт зберігаються атомарно в приватній схемі: create 30/годину, preview і list по 60/хвилину, accept 10/хвилину, revoke 30/хвилину. Невдалі preview/accept теж витрачають бюджет. Максимум 10 pending на простір; до 100 рядків у списку, активні першими. Прямий доступ до таблиць не наданий.

SQL перевіряє owner/member/outsider/anon, grants/RLS, приховані хеші, непридатність хешу як bearer, preview без членства, expiry/revoke/used, повтори operation_id й acceptance, бюджети, місткість, пріоритет активних рядків, виключення/новий вступ і збереження особистого простору.

На незалежних PostgreSQL-з'єднаннях перевірено: два одночасні прийняття дають рівно одне членство; revoke-first відхиляє очікуване прийняття; accept-first зберігає членство після revoke; виключення блокує старе pending-посилання; старий повтор виключення не видаляє нову епоху; 12 одночасних accept-запитів не обходять бюджет 10.

Браузер перевіряє створення/копіювання з ручним fallback/список/відкликання, втрату успішної відповіді створення й безпечний повтор, анонімне відкриття, прибирання fragment, cookie та захисні headers, відмову OAuth і змодельоване PKCE-продовження, явний вступ, вибір простору, збереження авторських прав, існуюче членство, invalid/revoked/used, мережевий повтор, інше посилання в тій самій вкладці, відсутність токена в IndexedDB та network URL/Referer.

Усі 6 тем перевірені на 360/390/768/1440 px: 24 комбінації, без горизонтального переповнення, focus і висота основної кнопки щонайменше 44 px. Збережено 26 PNG, включно з owner UI і входом. Дані на зображеннях — тестові.

## Відтворення

Запускати з shopik-app після production build. Тестові runtime встановлені окремо від залежностей застосунку: PGlite 0.5.13, Playwright/Edge, PostgreSQL 18.6 та pg. Нових бібліотек у застосунок не додано. Значення нижче — шляхи до відповідних ізольованих node_modules/каталогу інструментів, а не ключі робочої бази.

```powershell
$env:SHOPIK_SQL_MODULES = 'PATH_TO_SQL_NODE_MODULES'
$env:SHOPIK_BROWSER_MODULES = 'PATH_TO_BROWSER_NODE_MODULES'
$env:SHOPIK_PG_TOOLS = 'PATH_TO_PG_TOOLS'
node scripts/check-sql.mjs
node scripts/check-invite-concurrency.mjs
node scripts/check-invites.mjs
node scripts/check-shared.mjs
node scripts/check-local-store.mjs $env:SHOPIK_BROWSER_MODULES
```

Для збереження browser-артефактів можна задати SHOPIK_CHECK_OUTPUT. Browser fixture перехоплює звернення до Supabase локально; production build має відповідати .env.local. Native PostgreSQL script створює окремий тимчасовий кластер на loopback, застосовує міграції та зупиняє сервер після перевірки. Він очікує Windows binary package @embedded-postgres/windows-x64 і драйвер pg усередині SHOPIK_PG_TOOLS/node_modules. Для коректної Unicode-регресії використовується builtin C.UTF-8.

Sandbox блокує запуск Edge; браузерні перевірки виконані поза ним з дозволом. Жодних справжніх запрошень іншим людям не надсилали.

## Межі приймання та запуск

Міграція 202610310011_workspace_invites.sql ще не застосована до hosted Supabase. Вона має йти після 202610310010_shared_permissions.sql; старі міграції повторювати не потрібно. Перед запуском перевірити її на копії заповненої цільової схеми та виконати rollback SQL-тест.

Додати app callback із flow=invite до Supabase redirect allowlist, зберігши звичайний callback. Розгорнути код і міграцію узгоджено. Точні кроки наведені в docs/SUPABASE.md.

Симуляція OAuth підтверджує поведінку коду та обміну callback, але не налаштування Google/Supabase, cookies цільового HTTPS-домену чи реальний вибір Google-акаунта. Це потрібно перевірити на цільовому середовищі реальними акаунтами, включно з відмовою, повторним входом, прийняттям, відкликанням і новим вступом після виключення. Повний офлайн-вступ і Realtime не додавалися.
