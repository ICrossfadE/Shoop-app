# 011 — авторство, спільне завершення й виключення (31.10.2026)

Реалізацію виконано поверх актуальних WorkspaceApp, QueryCache, IndexedDB/чернеток 010A і apply_operation/list_snapshot 008. Збережені незакомічені зміни користувача в оформленні й хедері. Нових залежностей застосунку немає; PGlite 0.5.13 встановлено тільки в окрему системну тимчасову теку для тестів.

## Погоджені правила й результат

- Завершувати покупку може будь-який чинний учасник; чужі поля/теги при цьому не змінюються. Редагування/видалення продукту — тільки автору, включно з власником Workspace.
- Створювати й використовувати категорії можуть усі учасники; перейменовувати й видаляти — лише автор. Непорожні категорії захищені FK.
- Лише власник виключає іншого учасника. Його продукти й порожні категорії видаляються; категорії з чужими продуктами передаються власнику без переміщення продуктів.
- Витрати завершених продуктів виключеного учасника зберігаються з історичними сумою, валютою, датою, категорією, автором і тегами. SHA256 product_id залишається історичним ID джерела без FK до живого продукту. При звичайному видаленні продукту тригер прибирає його неархівну витрату. Клієнт не має прав змінювати archived або видаляти expenses.
- RLS, guard-тригер, прямий RPC save_product_tags, apply_operation і Server Actions узгоджені. UI не показує чужі edit/delete, зберігає спільне завершення й не пропонує видаляти архів.
- В налаштуваннях є публічні display-поля учасників, підтвердження виключення та вибір між уже чинними членствами. Email інших учасників не відкриваються. Cookie shopik-workspace — HttpOnly, лише перевага; сервер повторно перевіряє членство. Недоступний вибір повертається до особистого простору.
- Очищення QueryCache/IndexedDB/чернеток виконується при виявленому відкликанні, включно зі scope при SSR fallback. Перед перенаправленням очікується завершення очищення. Server-verified created_at членства є епохою для дискового відновлення: після нового вступу попередні snapshots і чернетки цього простору стираються. Інші простори не стираються при scope-очищенні.
- Видимий екран перевіряє метадані кожні 30 секунд і при focus/online/visibilitychange. Realtime не додано; офлайн-пристрій не може миттєво дізнатися про дистанційне відкликання.

## Безпека й атомарність

Усі звичайні записи беруть той самий Workspace advisory transaction lock, що й виключення, та перевіряють/блокують чинний рядок членства після очікування. remove_workspace_member перевіряє фактичного власника й роль owner, не дозволяє виключення власника, архівує витрати до видалення продуктів, передає зайняті категорії, видаляє порожні й відкликає членство в одній транзакції. Помилка відкочує всі кроки. Немає клієнтського прапорця обходу RLS чи довільної архівації. Очікувана дата вступу захищає від повтору старого виключення після нового членства.

Дизайн перевірено за документацією [PostgreSQL locking](https://www.postgresql.org/docs/17/explicit-locking.html) та [RLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html). Прочитані обидва AGENTS.md, задача 011, поточні документи/міграції/тести, local Next.js 16.3.4 guides про server/client components і mutating data.

## Застосування

1. Перевірити застосування попередніх міграцій 001–009. Міграцію 008 повторно не запускати, але її RPC мають існувати.
2. На копії наявної бази застосувати лише `supabase/migrations/202610310010_shared_permissions.sql`, потім виконати весь `supabase/tests/shared_permissions.sql` (ROLLBACK). Очікується `PASS: author rules, shared completion, atomic eviction, snapshots, RLS, retries and category transfer`.
3. Застосувати перевірену нову міграцію на робочому Supabase та розгорнути новий код разом із нею. Старий клієнт не отримує старих широких прав; помилки нових RPC до міграції не вважаються успіхом.
4. Перевірити реальні Google-сесії з двома/трьома акаунтами. Не створювати членства прямим записом із браузера: RLS/grants цього не дозволяють. Інвайти додаються наступним етапом.

## Межі приймання

Hosted Supabase не змінювався; реальні Google-акаунти, production PostgREST і незалежні конкурентні PostgreSQL-з'єднання не перевірені. PGlite виконує SQL/RLS, але не підтверджує міжз'єднанні перегони create/complete/remove: перед hosted-прийманням запустити ці операції паралельно на різних з'єднаннях і перевірити серіалізацію/rollback. Не перевірялися Firefox/Safari, велике навантаження й усі теми/ширини повторно.

Інвайти, прийняття запрошень, доставка змін через Realtime та повна офлайн-черга 010B/C не реалізовані цим етапом. Членство перевіряється на сервері для кожного запиту; миттєве дистанційне стирання вже завантаженої копії без мережі не гарантується.
