## Порівняння production-збірок

Початкова збірка коміту `933132c` і нова збірка Next.js 16.3.4 зібрані через Webpack. Chromium Headless 151 / Playwright 1.62.1, Node 24.14.0, однакові тестові дані, затримка 60 мс на кожен запит Supabase. Весь Supabase-трафік спрямовано в локальний адаптер PostgREST із PGlite 0.5.13. Це виконання справжнього SQL/RLS на ізольованих даних, але не вимірювання хмарного Supabase. Для Auth використовується окрема тестова RSA/JWKS-пара.

Пораховано звернення до Data API, а не внутрішні SQL-оператори, прочитані рядки чи тарифи. Час — один автоматизований UI-сценарій, включно з діями Playwright і 120 мс очікування стабілізації; це орієнтир, не статистичний benchmark. Появу оптимістичної картки перевірено до відповіді мутації.

## Реалізація

- Підтверджені списки плюс незалежні оптимістичні накладення для створення, редагування, завершення й видалення продуктів. Невдала операція відкочується окремо, інші картки та навігація доступні. Теги й категорії використовують `useOptimistic`.
- Root `CacheBoundary` зберігає чернетки продуктів і помилки мутацій при клієнтській навігації. Невідомий результат фіксує ключ і поля для безпечного повтору. Повне перезавантаження не зберігає чернетки: IndexedDB і офлайн-черга залишаються задачею 010.
- `apply_operation` повертає канонічний продукт із тегами, серверними ID/автором/датами. Кеш оновлюється цільово, без широкого `revalidatePath` для продуктів. Зміни довідників усе ще потребують серверної ревалідації залежних маршрутів і не входять у цифри продуктового benchmark.
- `list_snapshot` повертає лише рядки потрібного фільтра та їхніх авторів. Витрати, суми й категорії — один SQL snapshot. Оптимістичне видалення перераховує рядки й суми разом у копійках, зберігаючи різні історичні назви однієї категорії.
- Кеш у пам'яті браузера ізольований за акаунтом, Workspace, типом списку, категорією або місяцем/роком і нормалізованими тегами. TTL — 30 секунд. Свіжий кеш не робить запит; прострочений показується одразу й перевіряється у фоні. Однакові одночасні читання об'єднуються. Старі суми не підставляються під новий фільтр.
- URL залишається джерелом фільтрів. Підтримуваний Next.js Native History API оновлює `useSearchParams` без повторного RSC-рендеру довідників; back/forward перевірено.
- Focus та online інвалідують кеш і перевіряють поточний список. Мутації продуктів оновлюють product-кеші та інвалідують expense-кеші; зміни довідників інвалідують залежні списки. Мутація не подовжує свіжість сторонніх рядків. Помилка фонового читання залишає останні коректні дані.
- Logout, зміна акаунта та виявлена втрата доступу очищають приватний кеш, чернетки й операції. Пізня відмова старого акаунта не очищає новий. Кожен мережевий запит перевіряє чинну сесію, членство та RLS. Realtime-підписки немає; зміни інших учасників виявляються при повторному читанні/поверненні.
- React `cache` повторно використовує сесію/тему лише в межах серверного рендеру. `ensure_personal_workspace` для наявного простору має шлях читання без трьох спроб `INSERT ON CONFLICT`.
- SQL не переписує незмінені поля продукту та незмінені зв'язки тегів. Тести перевіряють незмінність `updated_at` і `ctid` зв'язків.
- Усунуто наявну розбіжність CLDR: Node віддавав `₴`, браузер — `грн`. Явний символ валюти прибрав помилки гідратації у новій перевірці.

## Вартість ідемпотентності

Нова успішна логічна мутація додає один службовий receipt у `shopik_private.operation_receipts`. Він містить SHA256 нормалізованого JSON-входу й мінімальний результат; для продуктів — ID, а не копію опису. Receipt і зміна комітяться однією транзакцією. Advisory lock серіалізує однакові ключі. Повтор перевіряє членство, не виконує зміну повторно та повертає актуальний продукт або його видалення, не відновлюючи стару картку.

Це додатковий запис і місце в базі. **75% менше Data API-звернень не означає 75% менше SQL-записів.** Економія записів отримана на незмінених тегах/полях. Для продукту без тегів receipt може збільшити кількість фізичних записів. Автоматичного очищення receipts немає: видалення без визначеного строку повторів могло б повернути дублікати. Схему `shopik_private` не додавати до exposed schemas.

## Перевірки та межі

Пройшли lint, typecheck, 31 Node-тест, production build через Webpack, production `test:smoke` із новим приватним API, всі 8 міграцій і всі 7 SQL-файлів у PGlite, browser regression на production-збірці.

Браузерні сценарії: CRUD/завершення; підтверджений стан після нової навігації; втрата відповіді й повтор без дублювання; чернетка при переході між сторінками; RLS-відмова з відкатом і збереженням форми; дві незалежні незавершені операції; фільтри під час збереження; back/forward; кеш категорій/місяців; невдале фонове читання без втрати списку; узгоджені витрати; теги/категорії та відкат непорожньої категорії. Мобільний `settings-after.png` переглянуто.

Node-тести додатково перевіряють TTL, дедуплікацію, ізоляцію ключів акаунтів/Workspace, пізнє читання після завершення, очистку при втраті доступу та відповідь попереднього акаунта. SQL: дві ідентичності, анонімна роль, відкликане членство, повтор ключа, змінений payload, каскад витрат і SHA256 ID.

Старі SQL-тести уточнено: власний профіль створюється тригером 006; RESTRICT може повертати 23001 поряд із 23503; тест атомарності тегів ін'єктує збій на зміні зв'язку, оскільки незмінені зв'язки більше не вставляються повторно. Перевірки ізоляції та відкату збережено.

Не виконано: застосування міграції на робочій базі, браузерний сценарій із двома справжніми Google-акаунтами, конкуренція окремих серверних PostgreSQL-з'єднань та hosted Supabase latency/load benchmark. PGlite не замінює повну hosted-систему Auth/PostgREST.

## Відтворення

Звичайні перевірки у `shopik-app`: `npm run lint`, `npm run typecheck`, `npm test`, `npx next build --webpack`, `npm run test:smoke`.

Інструменти fixture не додано в залежності застосунку. В окремому каталозі потрібні `@electric-sql/pglite@0.5.13` та `playwright@1.62.1`, а також браузер `playwright install chromium --only-shell`. Встановлення: `npm install --prefix <окремий-каталог> --no-save @electric-sql/pglite@0.5.13 playwright@1.62.1`.

У PowerShell встановити `SHOPIK_SQL_MODULES` і `SHOPIK_BROWSER_MODULES` на абсолютні каталоги `node_modules` цих тестових інструментів. За потреби `PLAYWRIGHT_BROWSERS_PATH` задає каталог браузера; `SHOPIK_CHECK_OUTPUT` — каталог результатів. Із кореня репозиторію: `node shopik-app/scripts/check-sql.mjs` та `node shopik-app/scripts/check-optimistic.mjs --after`. Порти 3190 і 3191 мають бути вільні. Для `--before`/`--both` потрібен `SHOPIK_BASELINE_APP` з окремо збереженою початковою production-збіркою. Раннер перехоплює весь Supabase-трафік локально та не змінює хмарну базу.

## Запуск у Supabase

1. Після вже встановленої 007 виконати лише нову `supabase/migrations/202610300008_optimistic_queries.sql` у SQL Editor. Вона транзакційна, наявні продукти й витрати не видаляє. Повторно міграцію не запускати.
2. У тестовому Supabase-проєкті виконати весь `supabase/tests/optimistic_queries.sql`. Фікстури завершуються rollback.
3. У `shopik-app` виконати `npm run test:supabase -- --optimistic`, потім перезапустити dev-сервер або розгорнути нову production-збірку.
4. Перевірити повільне з'єднання, повтор втраченої відповіді й два реальні акаунти. На робочій базі підтвердити виміри без тестового адаптера.
