# 017 — Мобільний інтерфейс і фактична ціна

Реалізовано й перевірено локально 01.11.2026. Hosted Supabase та production-деплой не змінювалися.

## Результат

- Головна: «Список продуктів», одна/дві іконки чинних учасників, компактний ряд керування фільтром і горизонтальний ряд тегів, незалежні акордеони категорій із відфільтрованими сумами.
- Спільний «+» на головній і витратах відкриває створення продукту, тегу та категорії. На settings його немає. Форми довідників перевикористовують чинні серверні операції; useId усуває дублювання ID зі змонтованими налаштуваннями.
- Два рядки картки: назва/ціна/галочка та аватар/дата `dd-mm-yy`. Довгий тап або контекстне меню відкривають авторські дії; клавіатурна кнопка залишається. Рух/scroll/pointercancel скасовують long press. Меню використовує top layer із 016.
- Витрати зберігають порядок і групування історії, періоди, AND-теги та історичні метадані. Статистика й налаштування мають адаптивні розміри. Шрифти/відступи зменшено без масштабування сторінки через transform/zoom; області натискання — щонайменше 44 px.
- Автор може змінити фактичну суму неархівної витрати. Окрема RPC змінює тільки Expense.amount. Product.price і дата/категорія/теги/автор незмінні. Сервер перевіряє права, expected_amount і ключ повтору; архівні витрати не редагуються навіть після повторного вступу автора.
- Підтверджена ціна оновлює всі відповідні кешовані періоди/теговi вибірки й підсумки в копійках; дискові snapshots інвалідуються. При відмові зберігається попередня підтверджена сума, при невизначеній відповіді — поля та той самий ключ для ручного повтору. Автоматичної офлайн-черги корекцій не додано.

Браузерний тест використовує headless Edge із локальним Auth/PostgREST адаптером і тимчасовою PGlite БД. Новий скалярний numeric у цьому адаптері приводиться до JSON number, як у PostgREST; це не зміна суми в застосунку. Native PostgreSQL fixture використовує окремий тимчасовий loopback-кластер, а не hosted БД. Секрети реальних акаунтів або справжні запрошення людям не створювалися.

## Повторний запуск

Із `shopik-app`, після production-збірки, з наявними ізольованими тестовими runtime:

```powershell
$env:SHOPIK_SQL_MODULES = 'PATH_TO_PGLITE_NODE_MODULES'
$env:SHOPIK_BROWSER_MODULES = 'PATH_TO_PLAYWRIGHT_NODE_MODULES'
$env:SHOPIK_PG_TOOLS = 'PATH_TO_NATIVE_PG_TOOLS'
$env:SHOPIK_CHECK_OUTPUT = 'PATH_TO_TEST_OUTPUT'
node scripts/check-sql.mjs
$env:SHOPIK_CHECK_MOBILE = '1'
node scripts/check-invite-concurrency.mjs
node scripts/check-invites.mjs
Remove-Item Env:SHOPIK_CHECK_MOBILE
$env:SHOPIK_CHECK_WORKSPACES = '1'
node scripts/check-invites.mjs
Remove-Item Env:SHOPIK_CHECK_WORKSPACES
node scripts/check-shared.mjs
```

PGlite, Playwright/Edge, PostgreSQL і pg беруться з раніше встановлених тестових каталогів. Нових бібліотек у застосунок не встановлено. Браузерні fixtures використовують порти 3190/3191, тому їх запускати послідовно.

## Застосування і межі перевірки

На цільовій БД після міграції 012 застосувати **лише** `supabase/migrations/202611010013_expense_price.sql`, потім виконати весь `supabase/tests/expense_price.sql` у тестовому проєкті та розгорнути нову збірку. Міграція додає приватну таблицю receipt-ів і вузьку RPC; існуючі ціни, покупки та ID не переписує. Старі міграції не повторювати.

Фактичний hosted Google/Supabase сценарій, iOS/Safari, фізична екранна клавіатура та апаратні safe area не перевірені. CSS враховує safe-area-inset і динамічний viewport, а короткий landscape перевіряє обмежену висоту форми. Кореневий текст 200% і синтетичний touch у Edge не є перевіркою фізичного телефону. Коригування ціни потребує мережі; після ручного reload безпечне відображення відновлюється з серверного snapshot, окремої постійної чернетки цієї форми немає.
