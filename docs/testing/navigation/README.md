# Швидка навігація — 30.10.2026

Реалізовано спільну WorkspaceApp для списку покупок, витрат і налаштувань. Шапка залишається змонтованою; звичайні переходи використовують Native History API, підтримуваний установленим Next.js 16.3.4. Прямі URL і перезавантаження залишаються серверними та перевіряють авторизацію. Ctrl/Cmd-click, нові вкладки, URL-фільтри, back/forward і посилання на секції збережено.

Налаштування використовують спільний bootstrap тегів, категорій і теми. Їх форма лишається змонтованою при переходах і зберігає незбережений ввід. Мутації тегів/категорій повертають канонічні дані в оболонку без широких revalidatePath; оптимістичні зміни та серверні перевірки збережено. Продукти й витрати використовують QueryCache із 009; відсутній initial snapshot не засівається порожнім успішним списком.

Через 500 мс готуються лише два основні списки (перша категорія без тегів і поточний місяць). Свіжі та одночасні запити пропускаються/об'єднуються кешем; за saveData або без мережі підготовка вимкнена. Це переносить мережеве читання до натискання і може додати до чотирьох Data API-звернень на початкове відкриття (по перевірці членства та snapshot для двох відсутніх списків). Усі комбінації фільтрів не передзавантажуються.

Кеш списків залишається ізольованим за акаунтом/Workspace/фільтром і має TTL 30 секунд. Завершення покупки інвалідує також уже підготовлений, але ще не відкритий екран витрат. Прострочений snapshot відображається зі станом фонового оновлення; на новому фільтрі чужа сума не показується.

Новий приватний GET /api/workspace перевіряє сесію, членство і RLS та повертає no-store. Довідники перевіряються у фоні при переході після TTL, focus/online; помилка залишає останні коректні дані, а втрата доступу очищає кеш і веде до входу. Відповідь, що почалася до локальної зміни довідників, не перезаписує новішу зміну. Зміна каталогів інвалідує залежні списки. Тема та logout зберігають наявний серверний шлях.

## Перевірка production-збірки

Використано Next.js production build --webpack, Playwright/Chromium і локальний ізольований PostgREST-адаптер із PGlite та затримкою 60 мс на Data API-звернення. Це не вимірювання потужності або мережі хмарного Supabase.

| Екран | Натискання → видимий заголовок |
|---|---:|
| Налаштування акаунта | 28 мс |
| Витрати | 58 мс |
| Список покупок | 37 мс |

Під час цих переходів не було document/RSC-запитів; перевірено тотожність змонтованої DOM-шапки. Додатковий повторний цикл зі свіжими даними зробив 0 звернень до Supabase. Це один автоматизований прогін, не гарантія такого самого часу на кожному пристрої. Перше повне відкриття, невідомий фільтр або повільна мережа все ще потребують отримання даних; великий міжсторінковий loading при звичайній навігації більше не використовується.

Пройшли 32 Node-тести, lint, typecheck у production build, production build --webpack, test:smoke з анонімною забороною /api/workspace та production browser regression. Браузер додатково перевірив зміну продуктів, витрати після завершення (50,00), відкат RLS, втрату відповіді й повтор, паралельні зміни, фонову помилку читання, метадані після створення категорії/тегу, непорожню категорію та збереження форми налаштувань між екранами. Помилок гідратації не було.

Відтворення: як у docs/testing/008-009/README.md, із окремими каталогами інструментів та SHOPIK_CHECK_OUTPUT для нового прогону. Раннер shopik-app/scripts/check-optimistic.mjs --after тепер також містить перевірки навігації. Нових залежностей застосунку або експериментальних налаштувань Next.js немає.

## Запуск

Нова SQL-міграція не потрібна; використовується вже застосована 008. Потрібно перезапустити локальний сервер або розгорнути нову збірку. Виміри dev-режиму не показові для швидкості production.
