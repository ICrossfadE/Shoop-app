# 016 — робочі простори та меню продукту

Дата: 31.10.2026. Реалізовано в коді й перевірено локально. Hosted Supabase, Google та налаштування Vercel не змінювалися.

## Результат реалізації

- Налаштування мають постійну незалежну секцію «Робочі простори»: назви, роль, особистий/запрошений тип, поточний вибір і короткий ідентифікатор для однакових назв. Помилка workspace_people не приховує цю секцію.
- Один особистий простір на акаунт створюється/відновлюється незалежно від чужих членств. Нова міграція 012 ремонтує відсутнє чи неправильне owner-членство лише у просторі фактичного власника; прямі клієнтські зміни членства заборонені.
- /login доступний також авторизованому користувачу. Є явний шлях до особистого простору й поле запрошення. Google OAuth із flow=personal замінює старий вибір спільного простору. Звичайний callback зберігає попередню політику, invite callback повертає до явного вступу.
- Вставлене посилання перевіряється за поточним origin, шляхом /invite, довжиною та єдиним fragment token. Сторонні адреси не відкриваються й не завантажуються сервером. Same-origin правило однаково працює для localhost і production HTTPS. Поле не зберігається в IndexedDB; контекст готується чинним HttpOnly POST-механізмом 015.
- Перемикання перевіряє членство на сервері, очищає кеш/чернетки акаунта та повністю перезавантажує оболонку. Незавершені мутації й неоднозначні результати блокують перемикання; відкриті продуктові форми потребують підтвердження очищення. Попередження пояснює очищення локальних даних. Чужі покупки не переносяться.
- Меню OrderCard використовує портал і native popover top layer, виходить за overflow/transform предків, розвертається над кнопкою біля нижнього краю та переобчислює позицію при resize/scroll. Збережено Escape, стрілки, outside click, focus і native modal редагування.

## Діагноз початкового повідомлення

Код ensure_personal_workspace ще з міграції 008 уже розрізняв особистий простір і запрошене членство. Тому сам факт повернення в спільний простір не доводить відсутність особистого: це може бути збережений вибір cookie. Чинний перемикач був вкладений у завантаження учасників і показувався лише для кількох просторів, а /login не давав вибору сценарію. Ці обмеження усунені, додане явне відновлення особистого.

Фактичний стан hosted-міграцій і точна причина проблеми в розгорнутому середовищі не підтверджені: доступу до його керування/SQL у цьому виконанні не було. Відсутність міграції або помилка RPC не приховуються як успішне створення.

Новий браузерний сценарій перевіряє: спочатку інвайт → особистий простір → перемикання між обома → reload → logout/login з personal marker; відновлення старого invited-only акаунта; доступність списку при помилці людей; відмову перемикання офлайн без зміни cookie; відмову для зовнішнього посилання та вхід у чинний invite flow через вставлення коректного посилання.

Меню перевірено в усіх 6 темах на 360/390/768/1440 px із примусовими overflow:hidden і transform у картки: воно всередині viewport у top layer, стрілки переміщують focus між діями, Escape повертає focus, редагування відкриває dialog і закриває popover. Список просторів знято на чотирьох ширинах без горизонтального переповнення. Разом з регресією 015 — 54 PNG, 24 invite-layout і 24 menu-layout сценарії. result.json відображає успіх локального fixture, а не hosted Google.

Початковий browser-тест меню залежав від випадкового першого ID категорії; тест виправлений на явну категорію потрібного продукту. Регресійний тест виключення очікує завантаження нового login DOM перед читанням IndexedDB. Це виправлення синхронізації тестів.

## Відтворення

З shopik-app, після production build, із зовнішніми тестовими runtime (нових app dependencies немає):

```powershell
$env:SHOPIK_SQL_MODULES = 'PATH_TO_SQL_NODE_MODULES'
$env:SHOPIK_BROWSER_MODULES = 'PATH_TO_BROWSER_NODE_MODULES'
$env:SHOPIK_PG_TOOLS = 'PATH_TO_PG_TOOLS'
node scripts/check-sql.mjs
node scripts/check-invite-concurrency.mjs
$env:SHOPIK_CHECK_WORKSPACES = '1'
$env:SHOPIK_CHECK_OUTPUT = 'PATH_TO_ARTIFACT_DIRECTORY'
node scripts/check-invites.mjs
node scripts/check-shared.mjs
node scripts/check-local-store.mjs $env:SHOPIK_BROWSER_MODULES
```

PGlite 0.5.13, Playwright/Edge, PostgreSQL 18.6 та pg встановлені в окремих тестових каталогах. Native script очікує Windows binary @embedded-postgres/windows-x64 і pg в SHOPIK_PG_TOOLS/node_modules, створює тимчасовий кластер на loopback, виконує перевірки й зупиняє сервер. Browser fixture підміняє всі Supabase звернення локально й читає публічний URL із .env.local для узгодження зі збіркою. Для Edge і native server у цьому середовищі використано дозволений запуск поза sandbox. Справжнім людям запрошення не надсилали.

## Перед розгортанням

1. Перевірити на цільовій копії бази попередні міграції та застосувати тільки нову 202610310012_personal_workspace_recovery.sql після 011. Виконати personal_workspace.sql цілком (ROLLBACK).
2. У Supabase URL Configuration додати точний production /auth/callback?flow=personal і dev-варіант; залишити звичайний callback та flow=invite. Google Cloud redirect до Supabase не замінювати app callback.
3. Розгорнути код і перевірити публічний Vercel-домен в інкогніто. Справжні Google login/відмову/зміну акаунта, allowlist та Secure cookies потрібно перевірити окремо на цільовому HTTPS-домені.

Повний офлайн-вступ, Realtime, кілька власних просторів, перейменування/видалення та передавання власності не додавалися. Створення/вступ/перемикання потребують мережі. Кросвкладкові зміни та нестабільний мобільний зв'язок на реальних пристроях залишаються додатковим hosted-прийманням; локальні перевірки не замінюють його.
