Збережені секції: login — особистий і спільний простір; витрати — місяць, теги, загальна сума, категорії, порівняння та історія з автором/датою/тегами/діями; налаштування — тема, теги, категорії, робочі простори, учасники й акаунт. На головній збережені категорії, фільтри, картки, описи, вибір покупок, створення та підсумок. Візуальні зміни не переписують історичний план або суму покупки.

## Авторизація

Перед змінами прочитано локальну документацію Next.js 16 Proxy та актуальні [Supabase SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs) і [Supabase sessions](https://supabase.com/docs/guides/auth/sessions). Збереження сесії та строк access JWT — різні механізми: чинний refresh token має дозволяти продовжити роботу після закінчення access token.

Встановлений `@supabase/ssr` уже задає cookie `Max-Age=400 днів`, `path=/`, `SameSite=Lax`, а браузерний клієнт використовує persistSession/autoRefreshToken. Штучно збільшувати вже довгий строк cookie або JWT не знадобилося. Зміни виправляють шлях оновлення токенів і підтверджену помилкову реакцію на збій членства. Hosted-значення JWT expiry, inactivity timeout і time-box session у цьому запуску не читалися й не змінювалися; якщо там установлено коротке обмеження сесії, його потрібно перевірити окремо на цільовому проєкті.

`scripts/check-session.mts` виконує справжній Proxy з реальними NextRequest/NextResponse і Supabase SDK, але відповідями ізольованого Auth. Перевіряє matcher сторінок/API, прострочений access token, запис нового refresh/session cookie в запит і відповідь, 400-денний Max-Age, повторний запит із цією cookie, no-store та очищення відкликаної сесії. Reload/reopen тут моделюється новим HTTP-запитом із збереженою cookie; це не перевірка фактичного перезапуску браузера або багатоденної сесії.

Спільні налаштування Supabase та код мобільного Auth 023 не змінені. Нових залежностей застосунку немає. Для SQL-стенду відновлено відсутню тестову залежність PGlite 0.3.14 в окремому тимчасовому каталозі, поза репозиторієм.

## Повторний запуск

Із `shopik-app`, після `npm run build`, із наявними тестовими runtime:

```powershell
node scripts/check-session.mts
$env:SHOPIK_SQL_MODULES = 'PATH_TO_PGLITE_NODE_MODULES'
$env:SHOPIK_BROWSER_MODULES = 'PATH_TO_PLAYWRIGHT_NODE_MODULES'
$env:SHOPIK_CHECK_POLISH = '1'
$env:SHOPIK_CHECK_OUTPUT = 'ABSOLUTE_PATH_TO_031_ARTIFACTS'
node scripts/check-invites.mjs
Remove-Item Env:SHOPIK_CHECK_POLISH
```

Стенд створює власну БД, використовує порти 3190/3191, перехоплює Supabase-запити й зупиняє власні процеси після завершення. Регресія 019 запускається тим самим стендом з `SHOPIK_CHECK_WORKFLOW=1` замість `SHOPIK_CHECK_POLISH`.
